
# MMI評価 概要 (06_mmi_overview.md)

本ドキュメントは、`file-manager-main` プロジェクトの現行およびターゲットアーキテクチャにおけるモジュール性の成熟度を、Modularity Maturity Index (MMI) を用いて評価し、その概要と全体的な所感をまとめたものです。

**【重要】評価の前提:**
本評価は、ソースコードの詳細な分析前に行われたものであり、主に設計書とアーキテクチャ定義から得られた情報に基づいています。したがって、各スコアは**仮説に基づく評価**であり、実際のコード構造とは異なる可能性があります。詳細なコードレビューを経て、スコアは更新されるべきです。

---

## 1. システム概要と評価対象

- **システム概要:**
  ScalarDB/DLを活用し、高い耐改竄性を持つファイル管理機能を提供するWebアプリケーション。現行アーキテクチャは、主要なビジネスロジックを持つモノリシックなバックエンド (`ScalarDB-FileManagement`) と、障害注入用のマイクロサービス (`ScalarDB-FileManagement_BFD`) で構成されている。

- **評価対象モジュール・ドメイン一覧:**
  - **現行構造 (As-Is):**
    - `ScalarDB-FileManagement` (モノリス) 内に論理的に存在する以下の5ドメインをモジュールとして評価。
      - ユーザー管理
      - グループ管理
      - ファイル・フォルダ管理
      - 共有管理
    - `ScalarDB-FileManagement_BFD` (マイクロサービス) を1モジュールとして評価。
      - BFD管理
  - **ターゲット構造 (To-Be):**
    - `03_target_architecture.md`で定義した以下の5つのマイクロサービスをモジュールとして評価。
      - IAMサービス
      - ファイルメタデータ・サービス
      - コラボレーション・サービス
      - 監査台帳サービス
      - BFD管理サービス

## 2. システム全体の平均MMI (概算)

| 構造 | 平均MMI (概算値) | 所感 |
| :--- | :--- | :--- |
| **現行構造 (As-Is)** | **49.0** | 各ドメインの責務が単一アプリケーション内に混在し、特に独立性と結合度の面で課題が大きい。変更が他に影響を与えやすく、デプロイの単位も大きいため、機敏性に欠ける。 |
| **ターゲット構造 (To-Be)** | **76.0** | 関心事の分離により、各サービスの凝集度と独立性が大幅に向上。サービス単位での自律的な開発、デプロイ、スケールが可能となり、システム全体の柔軟性と回復力が高まることが期待される。 |

## 3. MMIレンジ別解釈

MMIスコアの一般的な解釈は以下の通りです。

| MMI レンジ | 成熟度レベル | 説明 |
| :--- | :--- | :--- |
| **71 - 100** | **Mature (成熟)** | 高度にモジュール化されており、疎結合と高凝集を実現している。自律的な開発・デプロイが可能で、再利用性も高い。 |
| **41 - 70** | **Standard (標準)** | ある程度のモジュール性は確保されているが、結合度や独立性に課題を残している。リファクタリングによる改善の余地が大きい。 |
| **0 - 40** | **Requires Improvement (要改善)** | モノリシックで密結合な構造。技術的負債が多く、変更やスケールが困難。抜本的な再設計が推奨される。 |

## 4. 全体としての所感

### 強みと弱み
- **現行構造の強み:**
  - 開発初期においては、単一のリポジトリとデプロイメントパイプラインにより、セットアップや開発のオーバーヘッドが小さい。

- **現行構造の弱み:**
  - **密結合:** 全てのドメインが同じデータベーススキーマとアプリケーションプロセスを共有しており、一部の変更が予期せぬ副作用を生むリスクが高い。
  - **低い独立性:** ドメイン単位での独立したデプロイやスケールが不可能。一つの小さな変更でも、アプリケーション全体のテストとデプロイが必要になる。
  - **技術的負債の蓄積:** 時間の経過と共にコードが複雑化し、新しい機能の追加や変更がますます困難になる傾向がある（ソフトウェアエントロピーの増大）。

### ドメイン種類・カテゴリとの関係
- 現行構造では、**マスタドメイン**である「ファイル・フォルダ管理」が、ファイル操作、永続化、ScalarDL連携など多くの責務を抱え込んでおり、凝集度の低下、つまりMMIの低下を招く中心的な要因となっています。
- ターゲット構造では、この中心的なドメインを「ファイルメタデータ」と「監査台帳」に分割し、さらに横断的な関心事である「IAM」を分離することで、各サービスの責務が明確になり、システム全体のMMIが大幅に向上する設計となっています。特に、非同期で連携する**サポートドメイン**（監査台帳サービス）の分離は、疎結合を促進する上で非常に効果的です。

この評価は、ターゲットアーキテクチャへの移行が、システムのモジュール性を健全化し、長期的な保守性・拡張性を確保するために不可欠であることを示唆しています。
