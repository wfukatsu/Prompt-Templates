
# 移行計画 (04_transformation_plan.md)

本ドキュメントは、現行のモノリシックな `file-manager-main` アプリケーションを、`03_target_architecture.md` で定義したマイクロサービスベースのターゲットアーキテクチャへ段階的に移行するための計画を記述します。

---

## 1. 移行戦略 (Overall Strategy)

リスクを最小限に抑え、サービスを継続しながら安全に移行を進めるため、以下の戦略を組み合わせます。

- **Strangler Fig Pattern (絞め殺しのイチジクの木 パターン):**
  移行のコア戦略として採用します。まず、モノリスシステムの前面に **API Gateway** を配置します。最初はすべてのリクエストを既存のモノリスにルーティングします。そして、新しいマイクロサービスを一つ開発・デプロイするたびに、API Gatewayのルーティング設定を変更し、該当するリクエストを新しいサービスに振り向けます。このプロセスを繰り返し、最終的にモノリスのすべての機能が新しいサービスに置き換えられ、モノリスを安全に停止できるようにします。

- **Anti-Corruption Layer (ACL):**
  移行期間中、新しく作成されたマイクロサービスと既存のモノリスは共存し、互いに通信する必要があります。この際、互いのデータモデルや技術的負債が影響し合わないように、サービス間に **腐敗防止層 (ACL)** を設けます。ACLは、一方のシステムのモデルをもう一方のシステムのモデルに変換する責務を持ちます。

- **データ同期:**
  サービスを切り出す際には、データも同様に移行する必要があります。初期データの一括移行と、移行期間中の継続的なデータ同期（双方向または一方向）の戦略をスライスごとに検討します。

---

## 2. 段階的移行計画 (Migration Slices)

移行は以下の4つの主要なスライス（段階）に分割して進めます。

### Slice 1: IAMサービスの切り出し

- **目的:** 認証・認可という横断的で重要、かつ比較的独立した機能を最初に分離し、マイクロサービス化の基盤を築く。
- **手順:**
  1. `IAMサービス` を設計・開発。ユーザー、グループ、ロールの管理APIと、OAuth2.0/OIDCに準拠した認証APIを実装する。
  2. 既存モノリスのDBからユーザーとグループのデータを新サービスのDB（IAM Namespace）に一括移行する。
  3. API Gatewayを導入し、`/login`, `/users`, `/groups` など、IAM関連のAPIへのリクエストを新しい `IAMサービス` にルーティングする。
  4. 既存モノリスの認証機能を `IAMサービス` へのAPIコールに置き換える。モノリスは今後、`IAMサービス` が発行するJWTを検証してセッションを管理する。
- **リスク:** 認証基盤の変更は全機能に影響するため、入念なテストが必要。
- **検証メトリクス:** ログイン成功/失敗率、API応答時間、新旧両システムでのセッション維持状態。

### Slice 2: 監査台帳サービスの導入

- **目的:** 非同期・イベント駆動アーキテクチャを導入し、耐改竄性のコア機能を疎結合な形で分離する。
- **手順:**
  1. イベントバス（例: Kafka）をセットアップする。
  2. `監査台帳サービス` を設計・開発。イベントバスからファイル操作イベントを購読し、ScalarDLに記録するロジックを実装する。
  3. 既存モノリス内のファイル操作（作成、更新、削除など）を行う箇所に、イベント（例: `FileCreated`, `FileUpdated`）をイベントバスに発行するコードを追加する（**並行稼働**）。
  4. `監査台帳サービス` が正しくイベントを処理し、ScalarDLにデータが記録されることを確認する。
  5. 十分な検証期間を経て、モノリス内のScalarDL書き込みロジックを無効化する。
- **リスク:** イベントの取りこぼしや重複処理が発生する可能性。冪等性のあるコンシューマ設計が不可欠。
- **検証メトリクス:** イベントキューの滞留量、イベント処理のスループット、モノリスのDBとScalarDLのデータ整合性。

### Slice 3: ファイルメタデータ & コラボレーションサービスの切り出し

- **目的:** システムの中核であるファイル管理と共有機能を分離する。最も複雑で大規模なスライス。
- **手順:**
  1. `ファイルメタデータサービス` と `コラボレーションサービス` を設計・開発する。
  2. モノリスのDBからファイル・フォルダのメタデータと共有設定を、各サービス専用のDB（Namespace）に移行する。移行期間中のデータ同期戦略を慎重に計画する。
  3. API Gatewayのルーティングを段階的に変更する。まず `GET` 系の参照APIから始め、次に `POST`, `PUT`, `DELETE` といった更新系APIに広げていく（**Canary Release**）。
  4. 依存関係にある `監査台帳サービス` へのイベント発行は、モノリスから新しい `ファイルメタデータサービス` が担当するように変更する。
  5. 全てのファイル・共有関連のトラフィックが新しいサービスに向けられたことを確認し、モノリス内の該当機能を削除する。
- **リスク:** データの一貫性維持が非常に困難。ダウンタイムを最小限に抑えるデータ移行戦略が鍵。
- **検証メトリクス:** 新旧APIのレスポンス比較、データ一貫性チェック、パフォーマンス（CPU/メモリ使用率）。

### Slice 4: BFD管理サービスの統合とモノリスの廃止

- **目的:** 全ての機能をマイクロサービス化し、最終的にモノリスを廃止する。
- **手順:**
  1. 既存の `BFD管理サービス` を見直し、API Gateway経由でアクセスできるように修正し、認証も `IAMサービス` と統合する。
  2. モノリスに残っている機能（もしあれば）を完全に移行する。
  3. API Gatewayのルーティングからモノリスを完全に削除する。
  4. モノリスのアプリケーションと、モノリスが使用していたDBテーブルを廃止・削除する。
- **リスク:** 予期せぬ機能の残存。
- **検証メトリクス:** モノリスへのトラフィックがゼロであることの確認。

## 3. ロールアウト戦略と検証

- **Canary Release / Blue-Green Deployment:** 特にSlice 3のようなクリティカルな機能の移行時には、一部のユーザーにのみ新機能を公開するカナリアリリースや、新旧環境を並行稼働させていつでも切り戻せるブルーグリーンデプロイメントを採用し、リスクを低減する。
- **Feature Toggles:** 機能の有効/無効を動的に切り替える機能フラグを導入し、新機能への切り替えと切り戻しを容易にする。
- **Observability:** 移行の各段階で、`03_target_architecture.md`で定義した監視基盤（Logging, Metrics, Tracing）を活用し、システムの健全性を常に監視する。特にエラーレートとレイテンシの悪化には細心の注意を払う。
