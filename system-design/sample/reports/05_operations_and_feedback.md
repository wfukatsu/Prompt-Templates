
# 運用・評価・改善計画 (05_operations_and_feedback.md)

本ドキュメントは、ターゲットアーキテクチャへの移行後、システムの健全性を維持し、継続的に改善していくための運用、評価、フィードバックのプロセスを定義します。

---

## 1. オブザーバビリティ (Observability) 設計

マイクロサービスアーキテクチャでは、システムの振る舞いを外部から理解する能力、すなわちオブザーバビリティが不可欠です。以下の3つの柱を基本方針とします。

- **Logging (ログ収集):**
  - **方針:** 全てのマイクロサービスで**構造化ロギング (JSON形式)** を標準とします。
  - **実装:**
    - 各ログエントリに `service-name`, `timestamp`, `log-level` などの共通フィールドを含めます。
    - API Gatewayで生成した **Correlation ID** をリクエストのライフサイクル全体で引き回し、全てのログに含めることで、サービスを横断したリクエストの追跡を可能にします。
    - FluentdやLogstash等を用いてログを集約し、ElasticsearchやLokiのような中央ログ基盤に転送・保存します。

- **Metrics (メトリクス収集):**
  - **方針:** 各サービスの健全性を定量的に測るため、主要なパフォーマンス指標を収集します。GoogleのSREが提唱する**「4つのゴールデンシグナル」**を基本指標とします。
  - **収集対象:**
    - **Latency:** リクエストの処理時間 (p95, p99)。
    - **Traffic:** リクエスト数 (RPS/RPM)。
    - **Errors:** エラーレート (HTTP 5xxなど)。
    - **Saturation:** CPU/メモリ使用率、キューの深さなど、リソースの飽和度。
    - **ScalarDB/DL固有メトリクス:** トランザクションのアボート率、コミットレイテンシ、Contract実行時間なども収集対象とし、データ層の健全性も監視します。
  - **実装:** Prometheusを標準的なメトリクス収集基盤とし、Grafanaでダッシュボードを構築して可視化します。

- **Tracing (分散トレーシング):**
  - **方針:** サービスをまたがるリクエストのフローを可視化し、パフォーマンスのボトルネックやエラーの原因を特定しやすくします。
  - **実装:** **OpenTelemetry** を標準ライブラリとして導入します。各サービスはリクエストの開始時にトレース情報を生成・伝播させ、JaegerやZipkinのようなバックエンドに送信します。

## 2. 評価とフィードバックのサイクル

技術的な改善がビジネス価値に繋がるように、評価とフィードバックのループを確立します。

### 2-1. 主要評価メトリクス

| カテゴリ | メトリクス例 | 目的 |
| :--- | :--- | :--- |
| **ビジネスKPI** | ・ファイルアップロード成功率<br>・月間アクティブユーザー数 (MAU)<br>・機能利用率 (例: BFD検証機能の利用回数) | ビジネス目標の達成度を測る |
| **パフォーマンス** | ・APIエンドポイント毎のp99レイテンシ<br>・エラーレート | ユーザー体験とシステムの安定性を測る |
| **回復力** | ・平均故障間隔 (MTBF)<br>・平均修復時間 (MTTR) | システムの障害耐性と復旧能力を測る |
| **開発効率** | ・デプロイ頻度 (Deploy Frequency)<br>・変更のリードタイム (Lead Time for Changes) | 開発チームの生産性を測る |

### 2-2. ADR (Architecture Decision Record) 更新サイクル

- **目的:** アーキテクチャに関する重要な意思決定を記録し、将来の参照と議論の土台とします。
- **プロセス:**
  1. **記録:** 新しいマイクロサービスの追加、技術スタックの変更、重要な連携パターンの選択など、アーキテクチャに大きな影響を与える決定は、軽量なADRテンプレートを用いて文書化します。
  2. **レビュー:** ADRはPull Requestベースでチーム内でレビューされ、合意形成を図ります。
  3. **バージョン管理:** ADRはコードと共にGitリポジトリで管理します。
  4. **定期的な見直し:** 四半期に一度、既存のADRを見直し、現状のビジネスや技術環境にそぐわなくなったものがないか評価します。陳腐化した決定は `deprecated` (非推奨) としてマークします。

## 3. アーキテクチャの継続的改善

一度構築したアーキテクチャが永遠に最適であり続けることはありません。ビジネスの成長と変化に対応し続けるためのプロセスを定義します。

### 3-1. 再スライス・再設計ポリシー

サービスの境界が不適切になる兆候を早期に検知し、対応します。

- **見直しのトリガー:**
  - **ドメインロジックの漏洩:** あるサービスの変更が、常に他の複数のサービスの変更を連鎖的に引き起こす場合。
  - **過度なおしゃべり (Chatty I/O):** ２つのサービス間で高頻度の同期呼び出しが発生しており、パフォーマンスのボトルネックになっている場合。
  - **データの一蓮托生:** ２つのサービスが同じDBテーブルを頻繁に更新し、競合が発生している場合。
  - **サービスの肥大化:** 単一のサービスが多くの責務を抱え込み、開発やデプロイが困難になってきた場合（新たなモノリス化）。

- **改善プロセス:**
  - 上記のトリガーが検知された場合、関係者が集まり、**イベントストーミング**や**ドメインストーリーテリング**といったモデリング手法を用いて、ドメインとコンテキスト境界を再評価します。
  - サービスの分割や統合といった再設計案を立案し、ADRとして記録した上で、次の開発サイクルで実行します。

### 3-2. ドメイン種類の変化への対応

業務プロセスの変更は、ドメインの性質（例: パイプライン、ブラックボード、ダイアログ）を変化させる可能性があります。

- **検知:** 定期的なドメインモデリングセッションを通じて、ビジネスプロセスの変化を捉え、ドメインの性質に変化がないかを確認します。
- **対応:** 例えば、単純なCRUD操作（ダイアログ）中心だったドメインに、複数部署の承認フロー（パイプライン）が追加された場合、同期API中心の連携から、ワークフローエンジンやイベント駆動へのアーキテクチャ変更を検討します。このようなアーキテクチャ上の大きな変更は、ADRを通じて慎重に議論・決定します。
